# Space: native I64 byte-string increment

Base: e2e38dbb45991b0e6153cf11244f64ed5c7a983e.
Scope: one typed I64 argument. This is a partial native Space path, not
complete Harbour Space compatibility. Numeric truncation/dispatch is a
separate planned increment, not silently assumed here.

## Source semantics and implementation

Pinned Harbour core 694428e1c12f726675b19324d62167fa77d68185,
src/rtl/space.c: numeric argument is converted to signed size; positive sizes
return that many ASCII spaces; nonpositive sizes return empty. Invalid
argument uses Harbour's runtime argument error/substitution path. The native
increment agrees on the admitted I64 cases; it statically rejects unadmitted
argument kinds instead of implementing that runtime error/substitution API.

The checker requires exactly one I64. Parameter inference pins an integer
count consistently with existing typed count builtins. Move analysis reads
the argument without transferring any owner. The emitter evaluates it once
then calls hbc_space. Expression typing returns StrOwn, so ordinary locals,
returns, nested consumers and destruction use the existing owned-string
protocol. Proc metadata's safe-builtin list includes Space because it does
not inspect or call back into user frames; argument expressions are still
recursively checked for introspection.

hbc_space uses the already-published hbc_stralloc/hbc_strfill helpers; it
does not simulate Space with an intermediate Replicate value. Nonpositive
counts allocate a valid owned empty header; positive counts reserve the
exact output capacity and fill every byte with 0x20 before returning. The
result remains independent owned storage. Headers, counters, registry,
64KiB/two-way cache, TLS offsets, OS paths and fill helpers are unchanged.
No source/argument snapshot is needed because there is a single numeric
argument, and no callback runs after allocation. No new assembler opcode,
C runtime call, target or platform dependency is introduced.

## Reproduce

From BASE after applying CHANGES.patch:

```sh
rustc --edition=2021 -O src/hbc.rs -o /tmp/hbc-space
python3 tests/space/check.py --compiler /tmp/hbc-space \
  --hbmk2 /path/to/hbmk2 --output /tmp/space-check-new \
  --wine /path/to/wine --wine-prefix /path/to/prefix
python3 tests/space/abi.py --compiler /tmp/hbc-space \
  --output /tmp/space-abi-new
python3 tests/space/benchmark.py --compiler /tmp/hbc-space \
  --hbmk2 /path/to/hbmk2 --output /tmp/space-benchmark-new
rustc --edition=2021 -O tools/run_native_manifest.rs -o /tmp/run-manifest
/tmp/run-manifest --compiler /tmp/hbc-space --target linux \
  --manifest tests/manifest.txt --output /tmp/space-full-new
```

Existing cache/SubStr/trace gates accept --compiler,--hbmk2,--output and
optional --wine,--wine-prefix. The fill-perf checker additionally takes
--baseline (build unmodified BASE). Its legacy JSON base field names the
original performance package base; compiler hashes identify this fresh run.
All output directories must be new. Existing shell helper tests require
./hbc and their documented M/MLIB/WINE/WINEPREFIX setup. No released compiler
binary is replaced by this patch.

## Performance

Same-source Space(n) loop, three whole-process samples each, exact stdout
checked for Harbour/native/C every time. Local n is not a constant-folded
Space result. C uses malloc/memset and frees the previous result after the
new one is created; it does not implement a VM, cache, registry or owned
header. It is a reference, not identical physical/runtime work. No other
validation workload was launched by this task during the final benchmark;
the shared host is not a dedicated performance lab. Startup/shutdown is
included, and short samples are noisy. Raw samples/sources are packaged.

## Limits

Space is not complete: only exact arity one and I64 counts are admitted.
F64 truncation (including range/nonfinite behavior), NumLocal and Dyn numeric
runtime dispatch, invalid-argument substitution and ignored extra arguments
are not implemented. No claim that Harbour rejects the named negative shapes.
The NumLocal path may reject at the existing function/builtin ABI gate before
reaching Space's own type message, which is asserted as a named limit.

The 65537-byte case is just beyond the unchanged 64KiB exact-capacity cache:
25108.58ns versus Harbour 2312.70 and C 2397.08. This is a clear performance
loss, not parity. It is reported rather than increasing allocator retention
inside a new builtin. The planned sequence remains Space, StrTran, Val;
allocator expansion is a separate decision. Other >64KiB results and cache
collisions can likewise take the slower OS allocation path. No universal
speedup or performance beyond the measured rows is claimed. C still wins
some admitted cached sizes; timing variability makes near-parity fragile.

Cache retains at most 16 * 65552 bytes including headers per thread; new
Space does not enlarge that bound. Owned results are independent; no RC/COW.
Process-global TRY restrictions, existing owned-error leaks, numeric/ABI and
platform limits remain. Normal-path final memcheck0 is not exception-cleanup
proof. Instrumented MT is still rejected. No native Windows/Mac/ARM result,
Unicode/codepage expansion, main-manifest change or released binary update.
