# Fixes from the 0.11.4 reports (issue #1 DBF items and the three-case report)

Every case below was built by real Harbour 3.2 (mingw64, GTCGI) and by hbc
`--target=windows` from the same source and compared byte for byte on
native Windows.

## DBF (issue #1)

- **x7 `n := T->NDEC * 2`** (`local n := 0`). The local was typed as an
  integer, so the decimal field failed at run time ("NIL used as a
  number"). The Dyn pre-scan now counts a DBF field read (`dbffieldref`,
  `FieldGet`) and arithmetic over one as a Dyn source, like a call to a
  Dyn-returning function. The local becomes Dyn-wide and holds the
  decimal value. Harbour: `3.0000`; hbc now the same.
- **Printing a decimal Dyn value after another item** (`? k, k`,
  `? n, n + 1`) printed `0.00` for the second item on Windows. The legacy
  inline-double arm of `hbc_print_dyn` loaded `%xmm0` before calling
  `hbc_pflush`, which writes the pending separator through the Win64 API
  and may clobber `%xmm0`. The value is now loaded after the flush (both
  targets; two pushes also keep the call 16-byte aligned).
- **x3 `c := T->CCOD`** (`local c := ""`) was a compile error ("type
  mismatch in assignment"). A string local may now receive a DBF field
  read: a character field (owned tag-4 cell) moves in; any other field
  type stops with `Type error: field is not a character value` (Harbour
  would retype the variable; this static model names it instead).
- Gate: `tests/dbf/fields` gains `f11_local_decimal` (decimal field, field
  arithmetic and field sums into integer-initialised locals over every
  record); 11/11 identical.

Not done: **x4** (`dbSetOrder`) and **x5** (`dbGoto`, `FCount`) on the
native adapter. They need new functions in the embedded DBF C runtime;
the Linux blob is pinned to Ubuntu gcc 11.4 (`generated/recipe.json`) and
must be regenerated there. Both already work with `--harbour-rdd`.

## Three-case report against 0.11.4

1. **`LOCAL month := 11` rejected as "reserved by the code generator".**
   The reserved list protects helper LABELS: only names that become
   assembler symbols (functions, classes, MEMVARs) can collide. Locals,
   parameters, statics, block parameters and loop variables live in
   frame slots, so the check now applies only to the former. This also
   clears the threads probes mt05, mt06 and mt13 (a local named `val`):
   all three are now identical to Harbour on native Windows.
2. **`FUNCTION DateName(d); ? CDow(d)` rejected ("expects a date").** The
   date builtins (`DToS`, `DToC`, `Year`, `Month`, `Day`, `DoW`, `CDoW`,
   `CMonth`) now pin a bare parameter argument as a date, the way `Upper`
   pins a string. A parameter that is only printed (`? d`) still has no
   type evidence and is still rejected.
3. **`SToD("00000101")` became an empty date.** Harbour admits year 0 (a
   leap year). `hbc_date_pack` now accepts year 0; `hbc_date_days` and
   `hbc_date_from_days` shift by one 400-year era so the unsigned
   divisions stay valid for January/February of year 0; a result outside
   years 0..9999 is the empty date instead of garbage (`e - 366` printed
   `[?3196590]` before).

Known differences left (Harbour behaviour, measured):
- `CDoW()` of a date in January/February of year 0 answers the NEXT day
  name in Harbour (`DoW` 7 but `CDoW` "Sunday"); hbc follows the calendar
  (`Saturday`), consistent with `DoW`.
- A date before 0000-01-01 prints `00000000` from `DToS` in Harbour; hbc
  gives the empty date.
- Separate, older: `Month`, `Day`, `Year`, `DoW` print with width 10 in
  hbc; Harbour uses 3, 3, 5 and 3.

Tests: `tests/review0114/r1_local_builtin_names.prg`,
`r2_date_param.prg`, `r3_year_zero.prg` (expectations are Harbour's
output; Linux expectation = the same bytes with LF).
