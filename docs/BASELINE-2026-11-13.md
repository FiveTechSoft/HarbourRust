## Current marker after captured-base persistent array reads

Published compiler commit: `b2d9212ec1cddf2931a04e7b44c35d21532ea5c4`. `src/hbc.rs` SHA256: `5c15c1023f0b31ed90d5459b3cc8b9c2db57371805b61744c575dbdd9ec53bee`. Base: the captured-store compiler `e458bfb241dc38565d432e455b92bb3cc7571837` recorded below. Only `src/hbc.rs` changed (four additions, two deletions). Harbour syntax is unchanged.

An indexed scalar read from a persistent STATIC array now captures and retains its array payload before evaluating the index. Bounds and the read use that captured payload. The integer/logical/NIL pair is saved across release of the temporary retention, then returned with its tag and payload intact. A call in the index can therefore replace the root, or clear its last owner, without changing the array being read. Existing `HB_ISNUMERIC` and `ValType` cell handling uses this central read path. No array layout, runtime helper, return-inference algorithm or borrowing ABI changed.

Calls in read indices are now allowed when the index does not directly mention the root and passes existing type checks. Direct root mentions, Dyn-index inference limits, borrowing, root escapes, nested owned payloads and shared resizing retain their limits. This is scalar-read retention, not general array borrowing.

Recursive probes establish an I64 return before self-use; they do not establish general recursive Dyn-index support.
- The deliberately incorrect control retains the old payload but reloads the new root before bounds/read. Probe 61 then exits with a bound error, while Harbour and the candidate return the old second cell with its numeric display provenance and exit cleanly. This finite suite is not a general memory-safety or lifetime proof. Normal-exit zero-live assertions do not establish failure-path cleanup. Native Windows execution and forced refcount overflow were not tested. Cycles, threads, objects, exceptions, nested owned payloads, escaping roots and full by-reference support remain outside scope.
