Rust architecture.

HarbourRust is an ahead-of-time native compiler for Harbour, written in Rust. It is NOT a Harbour-to-Rust translator. Its ordinary path compiles supported Harbour source to x86-64 machine code with its own ELF, PE32+ or experimental Intel Mach-O writer. No Rust source is generated. Using an already-built hbc needs no Rust toolchain: Rust is the implementation language of the compiler, not an intermediate language for your program. The ordinary native path needs no Harbour VM or pcode interpreter. Supported cases are checked against the original Harbour compiler where evidence is recorded, with explicit limits and known differences. Unsupported forms are rejected; accepting a source is not proof of equivalent behavior.

Project snapshot: 18 November 2026, main 9e150aee. The upstream scan below is dated 14 November. The records below distinguish current source, earlier measurements and unverified platforms.

Compatibility comes before speed claims. The latest recorded upstream scan (14 November 2026, not re-run since) admits 32 of 1,041 unchanged original PRG files, all 32 under upstream tests/ (268 files). Of those 32 recorded Linux instrumented executions, 30 match exactly and two open error dialogues and time out. These are not 32 compatibility passes or Mac results. Most of Harbour is still outside this subset.

How it works

One front end, two code-generation paths.

The compiler, hbc, is written in Rust. Its ordinary path performs its own analysis, assembles machine code and writes the native executable. It does not generate Rust or pass your Harbour program through rustc.

1. Harbour source and preprocessing

Own preprocessor handles the implemented directives and transformations. Unsupported forms remain explicit limits, not a claim of full preprocessor compatibility.

↓
2. Tokenizer, parser and semantic analysis

Build a syntax tree, infer/check the supported types, and run the compiler's own move, ownership and borrowing checks. Reject unsupported forms before code generation.

↓
3a. Ordinary x86-64 backend

Emit x86-64 machine code with the own mini-assembler and native ELF, PE32+ or experimental Intel Mach-O writer. No external assembler or linker is needed on the native-only path; --external-as keeps the legacy binutils route.

3b. Experimental LLVM backend

An opt-in experiment selected with --experimental-llvm: the same checked front end, then LLVM IR for a bounded subset, including integer/logical signatures, fixed integer arrays and limited constant-string output. It rejects unsupported families. It is separate from the default native backend and is not available for Mach-O.

↓
4. Native executable with a small runtime

The ordinary native-only Linux path embeds its own freestanding helpers and uses system calls; optional C-extension and hbmk2 routes have separate dependencies. No Harbour VM is required. This is a small embedded runtime, not "no runtime".

Rust-inspired, not Rust by inheritance.

Being written in Rust does not automatically make generated programs memory-safe. hbc implements its own rules and runtime. Its ownership model is deliberately different from Harbour's unrestricted dynamic sharing in some cases; that remains compatibility work.

A different trade-off from harbour/core.

Harbour's established compiler and runtime support a much broader dynamic language and ecosystem. HarbourRust explores a smaller native path. The aim is familiar Harbour syntax and tooling, without pretending the current subset has equivalent capabilities.

Historical evidence, not a universal promise

Know the boundary

Recorded results, not a completion percentage.

Latest recorded upstream admission

The 14 November baseline records 32 admitted originals out of 268 files under upstream tests/, or 32 out of 1,041 in the full inventory. Recorded Linux instrumented executions: 30 exact stdout/stderr/exit matches, plus two error-dialogue timeouts. This is a dated scan, not a new full-corpus run on this page's snapshot.

1,892

Current regression manifest rows

At main 9e150aee (18 November 2026) tests/manifest.txt has 1,892 rows (non-comment lines), of which 1,261 are executable rows checked by tests/run_macho_arm64.py. The rest are compile rejections and other non-runnable kinds: these are inventory counts, not runtime or compatibility passes. The older 1,720/1,720 marker (14 November), the 1,657/1,661 result and four inherited failures are historical, not the current status.

Current source includes the Date/CToD port, bounded C Extend bridge, DBF/NTX/CDX through an own native adapter (the default on Linux and on the Windows target; DBF writes are bounded; the opt-in --harbour-rdd mode on Windows links Harbour 3.2's own RDD instead), threads on Linux and Windows, and classes on Linux and, with limits, on the Windows target (oracle fixtures captured under Wine; the candidate runs against them on native Windows in CI, a focused object-separator check, not a full class gate), and class programs compile for the Mach-O targets with Mac compatibility not established here, each with its own limits. Linux Date() and Seconds() use the local zone (TZ or /etc/localtime, measured 2026-11-18); unsupported zones answer UTC. This is not the complete Harbour runtime or a general library-compatibility claim.

Platform evidence is separate.

  • Linux x86-64: native ELF is the ordinary path. Dated regression and oracle results are linked below; no new full 1,892-row all-platform execution claim is made here.
  • Windows x86-64: the tracked bin/hbc.exe has a focused Wine 11.0 verification, not native-Windows verification of that exact binary. An earlier Windows 11 manifest run is a separate result, not interchangeable evidence.
  • macOS Intel x86-64: own Mach-O writer and Darwin lowering are experimental. Structural checks and Linux syscall-model/proxy checks are not real-Mac loading or execution. On 17 November 2026 a GitHub Actions macOS Intel runner reported 1,274 passes in the ARM64 record (run 44032525274), including FILE, DBF, threads and EXTERNAL programs; that is not a certification on every Mac. Classes, current-date and CurDir paths keep explicit target limits.
  • ARM64: native --target=macho-arm64 output is in main (16 to 17 November 2026), not in the v0.11.4 release. src/harm64.rs translates hbc's x86-64 subset to AArch64 at compile time; GitHub Actions on Apple Silicon (macos-15) reported 1,264 passes (run 43985696680) and then 1,274 (run 44032525274). Named limits are in the ARM64 record; this is not full Harbour parity.

Issue #1 re-check, 18 November.

Main on native Windows 11 against Harbour 3.2: 34 probes taken from the ERP coverage report (not its full 117-probe kit). 10 byte-identical, 23 rejected at compile time with a message, 1 rejected at run time with a message, 0 silent mismatches. String accumulation (c += "b" on a literal-initialised local) now compiles and matches Harbour. Native DBF seek/goto, PRIVATE, BEGIN SEQUENCE and SET DATE are still rejected.

The goal is broader Harbour-source compatibility through familiar tooling. The bounded hbmk2 adapter is a separate toolchain path, not proof that every original program works. Unsupported dynamic behavior, platform differences and backend-specific limits remain explicit.

Try the implemented subset

Use hbc without MinGW.

The Windows x86-64 compiler is tracked in the repository at bin/hbc.exe. From a checkout on Windows, supported native-only programs need no Rust, MinGW, C compiler, external assembler or linker:

bin\hbc.exe tests\samples\hello.prg hello.exe
hello.exe

This is the main-branch snapshot built from source e17223f and added in 8299ee4, not the old v0.1.1 compiler. For a newer compiler use the v0.11.4 release (16 November 2026) or build current source. It is not automatically rebuilt when source changes. Wine 11.0 verification of that exact compiler covered hello and four positive TRY programs with exact expected output/empty stderr/exit 0, plus two compile-negative TRY cases. It was not a native-Windows or full-manifest run. Full source pin, hash and verification scope.

For supported native-only programs, the own writers produce ELF (Linux x86-64), PE32+ (Windows x86-64) and experimental Mach-O (macOS Intel x86-64), without external assembler/linker tools. Cross-target output remains subject to each target's supported boundary. The tracked Windows compiler defaults to PE32+; explicit targets select cross-output. PE imports are limited to the measured kernel32 whitelist; no CRT, SEH, TLS or base relocations are supported. Intel Mach-O and native ARM64 output ran on GitHub Actions macOS runners (see Status); the v0.11.4 compilers predate native ARM64.

Build the Linux compiler from source

Building the compiler needs Rust; using its native-only writer does not need GNU binutils:

rustc --edition=2021 -O src/hbc.rs -o hbc
./hbc tests/samples/hello.prg hello --target=linux
./hello

--external-as keeps the legacy assembler/linker path. Its Windows route still needs MinGW-w64 binutils and kernel32 import libraries. C extensions and the hbmk2 adapter have their own C-toolchain requirements.

All nine historical releases (v0.1.0 through v0.8.0) and their uploaded assets were removed on 14 November 2026; Git tags remain as source history. The latest release is v0.11.4 (16 November 2026), with Windows x86-64, Linux x86-64 and macOS Apple Silicon compilers and a SHA256SUMS.txt. You can also use the repository's tracked Windows compiler or build current source. Historical v0.1.1/v0.2.0 compilers wrote assembly even when the output was named .EXE; their build.bat needed external MinGW-w64 tools. Do not use that historical script for the current native-only quick start.
