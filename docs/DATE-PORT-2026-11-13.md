# Date/CToD port to the current compiler ABI

Status: local candidate, awaiting independent review. Base experiment commit:
`46e465228aac8009f85301be0d4585715b40315e`. This is an independent MIT
increment, not a merge of the old Date implementation into the new ABI.

## Contract

- `Date()` and `CToD(string)` produce a separate Date scalar. Locals,
  assignment, same-Date comparisons, Date-returning functions, `Empty`,
  `ValType` and existing output channels are covered in the bounded forms tested.
- Own representation: eight-byte packed YYYYMMDD, zero for empty. It does not
  reuse the older Date implementation's calendar payload or algorithms.
  Existing I64/display-provenance slots stay 16 bytes; Block and Dyn ABIs do
  not change. CToD consumes then releases owned temporary strings.
- Independent byte-oriented parser, calendar validation and formatting were
  written against black-box observations. No Harbour implementation source is
  translated. Gregorian month lengths/leap divisibility are implemented directly.
- Default CToD behavior measured here: up to three digit runs, unsigned32
  modulo accumulation, nondigit separators, NUL ends the input, years below 100
  add 1900. Output is mm/dd/yy; empty dates render two blank fields/separators.
  This is not configurable SET DATE/EPOCH support.
- Ten older own rejection fixtures remain conservative: Date parameters/byref,
  arithmetic, mixed comparisons/assignment/returns, array/hash storage and
  malformed calls are not newly supported. General Dyn Date storage is not
  added. Both LLVM modes reject Date; ordinary Windows code generation alone
  does not establish Windows correctness.

## Explicit Date() limits

Linux Date() and Seconds() use the local zone (changed 2026-11-18; the sections below dated 2026-11-13 describe the earlier UTC contract, which no
longer holds on Linux). The native helper reads Linux syscall 201 (or clock_gettime for Seconds), adds the offset from `hbc_tz_off`, and converts days from
1970 by year/month iteration. `hbc_tz_off` takes the zone from the TZ variable of the initial environment (read from /proc/self/environ):
`Area/City` is /usr/share/zoneinfo/Area/City, an absolute path is used as is, a leading ':' is skipped; with TZ unset it reads /etc/localtime.
The file must be TZif version 2 or later; the 64-bit transition block is searched.
Measured 2026-11-18 (tests/seconds/fixed_clock.py: 30 instants x 36 environments against Python, and the real ELF next to the oracle, Harbour
3.2.1dev r2610242111): Europe/Madrid, America/New_York, Asia/Kolkata, Pacific/Auckland, Pacific/Kiritimati (+14), Pacific/Pago_Pago (-11), an
absolute path, TZ unset (/etc/localtime), the exact instants of the 2026 DST changes, a day change, and instants from 1970-01-01 (local seconds
negative west of Greenwich; the calendar day is computed with a 400-year shift, so 1969-12-31 is correct). Date() agrees with the oracle in those
environments; Seconds() is checked against a Python window (its value changes every run), not against the oracle's value.
Every failure answers UTC, never an error: a POSIX TZ string without a file (`CET-1CEST`; the oracle does honour it, so this differs), an empty TZ,
a name containing `..`, an unknown zone, no readable /proc/self/environ, an environment over 64 KiB or a zone file over 64 KiB (read to EOF, never
truncated), a read error, a file that is not a regular file (a FIFO or device; opened O_NONBLOCK and checked with fstat), a TZif version 1 file or
one with a bad second header, a truncated file, no types, transitions not strictly increasing, a type index out of range, an offset beyond 26 h.
When TZ is unset, a missing /etc/localtime also answers UTC. The zone buffers live on the caller's stack (about 128 KiB per call), so concurrent
calls from threads share no state (measured with four threads). After the last transition of the file this reader uses the type of that
transition and does not read the POSIX rule in the file's footer: a "fat" file (the system's Europe/Madrid carries transitions to 2037) is exact until
then; for a "slim" file, dates after its last transition (typically 2007 for Madrid) can be off by the DST hour because of this reader, not
because of the file. Windows is unchanged (GetLocalTime). The Darwin helpers are unchanged and remain UTC.

Windows emits GetLocalTime and reads SYSTEMTIME year/month/day, but no Windows
object/link/runtime check was possible with the available local installation.
No native Windows or Wine pass is claimed. Synthetic Linux clock substitutions
are tests of the conversion, not end-to-end clock or Windows evidence.
