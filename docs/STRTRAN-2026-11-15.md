# StrTran: typed 2/3-argument byte replacement

Base: 6ed2de408627083bb9db7bb7ffe336be56707ea4.
This is a partial native StrTran path. It is not complete Harbour StrTran.

## Admitted semantics

Two or three typed string arguments: StrTran(text,seek[,replacement]). Omitted
replacement is empty (deletion). Matching is byte-exact and nonoverlapping;
replacement bytes are not recursively searched. Empty seek or seek longer
than text leaves text unchanged. Empty text stays empty. Embedded NUL and
0xFF are ordinary bytes, not terminators. Every native result owns independent
storage, even where Harbour may return a shared original item.

Grounding: pinned Harbour core 694428e1c12f726675b19324d62167fa77d68185,
src/rtl/strtran.c, plus fresh real Harbour outputs. Harbour also supports
occurrence start/count and additional dynamic/default/error behavior; those
are deliberately outside this package. Do not infer their semantics from the
admitted path or call an unadmitted form a Harbour error.

## Implementation and ownership

The checker admits arity 2/3 and string/owned-string values, inference pins
string parameters, move analysis borrows arguments and expression typing
returns StrOwn. Evaluation runs once left-to-right. Earlier nonvariable owned
results stay alive through the call. Earlier borrowed values are independently
snapshotted if any later expression may have effects. The existing conservative
expr_has_call includes calls, Seq, Set and unknown forms, not only explicit
byref calls. Pure later arguments avoid unnecessary snapshot allocation and
cache conflicts. Prior owners are released only after preserving the result.
The third argument is last and can remain borrowed; an owned third temporary
is released afterwards. The omitted replacement has length 0 and is never read.

One-byte patterns have tight count/fill kernels for empty/one/two-byte or
general replacements. A two-byte-pattern search fast path avoids generic
per-byte match setup. Other patterns use bounded byte search twice: first
count nonoverlapping matches, check signed result-length arithmetic, then
allocate and fill. Prefix bytes and large replacements use rep movsb; zero
prefix copies are skipped and short replacements use explicit byte stores.
No 16-bit store optimization is included. No search can read beyond the
remaining text, and each successful match advances by the full seek length.
The general search remains O(text length * seek length) in the worst case.
This is not KMP, a vectorized matcher or a universal best-search claim.

Allocation uses the already-published hbc_stralloc/hbc_strcpy helpers. All
result bytes are initialized before return. Headers, logical registry/counts,
64KiB/two-way cache capacity, TLS, flush policy, source-retention fixes and
other string emitters are unchanged. No new assembler instruction, platform
API, dependency, released binary or main-manifest change is introduced.

## Fresh correctness evidence

- Full Linux instrumented regression manifest: 1729 unique sources, 1729 pass.
- StrTran gate: 37 exact executions and 22 named rejections. Four pure programs
  run in Linux/PE normal/instrumented with four corresponding Work wrappers
  requiring final hb_memcheck0 after owners release (32 executions), plus
  five repeated normal MT runs with two simultaneous workers.
- Systematic byte program: 336 transforms including empty data/seek/replace,
  overlap, repeated prefixes, deletion, growth, NUL/0xFF, no matches and exact
  65535/65536/65537-byte boundaries. Raw OutStd compares EVERY result byte.
- Seed 19324 random program: 240 reproducible ASCII text/seek/replace triples,
  including empty operands and repeated-prefix patterns. NUL/0xFF are covered
  by the systematic program, not falsely attributed to the ASCII generator.
- Order/lifetime program:observable left-to-right argument evaluation, source
  changed byref while evaluating seek, seek changed while evaluating replace,
  owned nested argument results, user-function consumer and large aliases.
  Two >64KiB cases retain the source before replacement mutates it, including
  source and seek referring to the same owner. Fresh Harbour output wins.
- Eleven negative shapes per target:arity0/1/4/5, nonstring text/seek/replace,
  Dyn, F64 text, logical seek and NIL replacement. Each fails with the named diagnostic, no panic or emitted program.
  Start/count4/5 and some values Harbour accepts are deliberate rejections.
- GNU as/ld helper canaries: 40 (20 cases x normal/instrumented), checking
  exact full bytes, headers, callee-saved registers, caller stack restoration
  and logical allocation/free balance. Covers generic and specialized kernels,
  empty seek/text, overlap, NUL and replacement lengths 0/1/2/3/129.
- Existing gates:Space 21 exact+16 rejections; cache/ERP 49+3;
  fill/retention 28 before/after pairs + 28 final 0 wrappers and five worker runs;
  SubStr 64 exact+12 rejections; trace 28 exact. All identify final candidate.
- Existing ABI/cache-registry/pre-store-overflow helpers pass Linux+PE Wine.
- Four new composite error probes explicitly record nonzero final hb_memcheck:
  source retained then nested SubStr fails: 2; source+seek retained then nested
  replacement SubStr fails: 3, on both Linux/PE instrumented. These combine
  StrTran retained owners and SubStr's own snapshot; counts are not attributed
  wholly to one helper. They are NOT successful ownership tests. Existing
  retained-count and SubStr error probes remain separately nonzero as before.

Harbour oracle: core694428e1c12f726675b19324d62167fa77d68185 hbmk2 -gtstd,
-mt for workers. Wine is PE execution, not native Windows. No native Mac/ARM,
unrestricted compatibility or upstream program-admission claim. The 1729 is
our regression-manifest count, not the 1,041 upstream .prg inventory or 268
files directly under upstream tests/; those remain separate denominators.

A failed draft used long Chr concatenation expressions in its random fixture
and hit compiler timeouts. The final seeded ASCII-literal fixture avoids that
unrelated compile-shape issue and passes; no timeout is counted as a success.
A draft short-copy optimization was rejected by the NUL all-byte gate and
removed before final validation. No assembler-correctness fix is claimed.

## Reproduce

After applying CHANGES.patch on BASE:

```sh
rustc --edition=2021 -O src/hbc.rs -o /tmp/hbc-strtran
python3 tests/strtran/check.py --compiler /tmp/hbc-strtran \
  --hbmk2 /path/to/hbmk2 --output /tmp/strtran-check-new \
  --wine /path/to/wine --wine-prefix /path/to/prefix
python3 tests/strtran/abi.py --compiler /tmp/hbc-strtran \
  --output /tmp/strtran-abi-new
python3 tests/strtran/benchmark.py --compiler /tmp/hbc-strtran \
  --hbmk2 /path/to/hbmk2 --output /tmp/strtran-benchmark-new
rustc --edition=2021 -O tools/run_native_manifest.rs -o /tmp/run-manifest
/tmp/run-manifest --compiler /tmp/hbc-strtran --target linux \
  --manifest tests/manifest.txt --output /tmp/strtran-full-new
```

Existing Space/cache/SubStr/trace checkers accept --compiler,--hbmk2,--output,
optional --wine,--wine-prefix. Fill-perf additionally takes --baseline built
from unmodified BASE. Existing shell helpers use ./hbc and documented
M/MLIB/WINE/WINEPREFIX variables. Output directories must be new.
Unmodified BASE rejects StrTran as unknown; there is no honest native before
throughput measurement for a missing builtin. That baseline rejection is
recorded; the performance comparisons are against Harbour and a C reference.

## Benchmark

Twenty-six workloads: one-byte replace/expand/delete/miss at 8/64/256/4096/65536
source bytes; multibyte replace/growth at 256/4096; adversarial 31-byte common
prefix plus mismatching final byte at 256/4096. Three whole-process samples,
median ns/call; exact stdout checked for every run. Raw samples and generated
sources are packaged. No other validation workload was launched by this task
during the benchmark, but the machine is not a dedicated performance host.
Scheduler/load/thermal noise and launch/shutdown are included; short samples
and near-parity results are especially noisy.

C uses malloc, two-pass nonoverlapping memcmp matching and memcpy for the same
returned bytes. It does not model the VM, registry/cache, headers, parameter
evaluation or defensive retention. It is a reference, not equivalent physical
work or a general fastest-C implementation. The benchmark source is ASCII;
the separate correctness gate covers binary bytes. No speedup of a whole app
or all future text distributions follows from these rows.

## Limits

Arity4/5 occurrence start/count, Dyn/coercion and invalid-argument runtime
substitution are not implemented. Third NIL/nonstring defaults accepted by
Harbour are rejected rather than silently coerced. This is not full StrTran.
Raw byte matching is not Unicode normalization or codepage-aware searching.

The measured candidate beats Harbour on these 26 workloads, not every possible
text/seek/replacement. C is much faster on several multi-byte and repeated-
prefix rows. The general O(n*m) search can be poor on other adversarial data;
there is no vector-search/KMP guarantee. Empty/no-match results still copy
under this ownership model while Harbour may share them. Effectful argument
expressions can require additional snapshots not present in pure benchmark
arguments. >64KiB outputs and cache collisions may use slower OS allocation.
The unchanged cache retains at most 16 * 65552 bytes including headers per
thread; it is not enlarged here. No RC/COW or in-place result aliasing.

General TRY owned cleanup remains absent. If later argument evaluation
throws, retained values can leak. The own composite probes report 2/3 owners
rather than 0; the nested SubStr snapshot contributes too. Normal-path final 0
wrappers are not exception-safety proof. No error-path allocation sweep is
added or hidden behind these tests. Instrumented MT remains rejected under
its existing global-registry restriction; MT TRY admission is not expanded.

Whole-process microbenchmarks vary with shared-host scheduling and startup,
not application-wide speedups. Wine is not native Windows. No native
macOS/ARM, released binary replacement, main-manifest edit, upstream source
admission or complete-library compatibility/performance claim is made.
