# Native ARM64 Mach-O backend (Apple Silicon), 16 November 2026

`--target=macho-arm64` (the default for an hbc built on Apple Silicon)
now writes a native arm64 Mach-O executable instead of rejecting.

## Design

hbc's code generator and its runtime emit one fixed x86-64 subset, the same
text the own assembler `hasm` encodes. `src/harm64.rs` (a child module of
`hasm`, reusing its parser) translates that subset instruction by instruction
into AArch64 at compile time. There is no run-time emulation and no x86 code
in the executable.

- Registers: x86 GPRs map to fixed ARM registers; `rsp` is x28 and addresses
  an emulated stack (64 MiB, mmap'ed at start-up), so push/pop/call/ret keep
  their 8-byte slot layout. `call` stores the return address in that slot and
  uses `bl`, `ret` reloads it and uses `ret`, so the hardware return predictor
  still works. xmm0-15 map to v0-v15. The real `sp` is only used to call
  libSystem.
- Flags: no flags register is emulated. A backward search over the control
  flow graph pairs each consumer (jcc, setcc, cmovcc, sbb) with its producers;
  only those producers use flag-setting ARM forms, and the condition is mapped
  through the producer kind (subtract, add, logic, inc/dec, imul overflow, FP
  compare, bit test, shift). Unknown or mixed pairings are compile errors.
  Translations that clobber NZCV internally preserve it when flags are live.
- System calls: Linux numbers are lowered to Darwin `svc #0x80` at compile
  time (write, open with flag conversion, close, mmap, munmap, exit, fcntl,
  gettimeofday). Anything else is a compile error.
- x87: the runtime only uses four fixed x87 idioms (pow, exp2, y*log2(x),
  fmod). They become calls to libSystem `pow`, `exp2`, `log`/`log10`/`log2`
  and `fmod` through one register-preserving wrapper.
- Mach-O: own writer. PIE, `__PAGEZERO`/`__TEXT`/`__DATA`/`__LINKEDIT`,
  dyld info rebase (absolute pointers in data) and bind (libSystem imports),
  `LC_MAIN`, `LC_BUILD_VERSION` (macOS 11), and an ad hoc SHA-256 code
  signature. No Apple linker, assembler or codesign is used.

## Evidence

- All 1209 runnable manifest rows (pos, posx, pos2, posx2, streams,
  streams2) compile with `--target=macho-arm64 --instrument` and produce the
  exact Linux expected bytes and exit codes when run under a Unicorn arm64
  user-mode harness with a Darwin system-call model: 1209/1209, counted twice
  (runner summary and results file).
- x86 Linux and Windows assembly is byte-identical to `origin/main` for all
  1822 manifest programs on both targets (3644 compilations).
- capstone disassembles every emitted word (no invalid encodings).
- Real Apple Silicon (GitHub Actions macos-15, run 43976128987, job
  `native-arm64`): the loader, dyld binding of libSystem and the ad hoc
  signature are accepted (`codesign -v`: "valid on disk", "satisfies its
  Designated Requirement"), and `tests/run_macho_arm64.py` reports
  `SUMMARY {'PASS': 1209}` with no REJ or FAIL rows.

The emulator proves instruction semantics, not Darwin loader or kernel
acceptance. `tests/run_macho_arm64.py` is the native runner for Apple Silicon
hardware (CI or a Mac): it compiles every runnable row, runs it natively and
applies the same acceptance rules as `tests/run_battery.sh`.

## FILE, DBF, threads and EXTERNAL (17 November 2026)

- System calls whose number is not a constant at the `syscall` (the gcc
  runtime blobs), or that need argument or structure conversion, go to
  a run-time dispatcher, `__a64_linux_syscall`. It is written in the same
  x86 subset and translated with the program, and it handles:
  - openat flags and `AT_FDCWD`;
  - fstatat64 to the Linux `struct stat` layout;
  - getdirentries64 to `linux_dirent64`, in place;
  - clock_gettime through gettimeofday;
  - mmap flags.

  A raw Darwin call is spelled `mov $0x2000000+N, %eax; syscall`.
- The DBF blob needed more translations:
  - `ud2`, 8/16-bit shifts and shifts by `%cl`, `adc`, `bswap`;
  - one-operand `imul`, `bt` on memory, `rep movs`/`stos` in q/l/w;
  - `ror`/`rol`, FP-parity `cmov`, `movapd`.

  Non-PIC `movl $symbol, %reg` keeps the full 64-bit address.
- Threads:
  - `clone` becomes `pthread_create`. The child resumes after the
    syscall with the parent's registers and `rsp` = child stack.
  - `%fs` is a per-thread base register (x7), set by `arch_prctl`.
  - futex maps to `__ulock_wait`/`__ulock_wake`. `exit` in a worker is
    `pthread_exit`; `exit_group` ends the process.
  - Locked read-modify-write, `xchg` with memory and `cmpxchg` are LL/SC
    loops followed by a full barrier.
  - In programs that use threads, shared-memory loads are `ldar` and
    stores are `stlr`. That is at least as strong as x86 TSO.
- EXTERNAL:
  - The C extension and `extend/hbhbr.c` are built into one dylib, which
    the executable loads as its second dylib:

        clang -O2 -dynamiclib -undefined dynamic_lookup -Iextend \
              extend/hbhbr.c myext.c -o libhbext.dylib
        hbc prog.prg prog --target=macho-arm64   # loads @executable_path/libhbext.dylib

    `--ext-dylib=NAME` sets another install name.
  - `HBHBR_FN_*`, `hbc_ext_end` and the bridge data words bind through
    the GOT.
  - Calls into C go through a thunk that maps SysV argument registers to
    AAPCS64. The executable exports C-callable `hbc_strcpy`,
    `hbc_freestr` and `hbc_blk_launch`.
  - EXTERNAL together with threads works since 17 November (below).

Evidence on Apple Silicon (GitHub Actions macos-15, run 43985696680, job
`native-arm64`), from `tests/run_macho_arm64.py`: `SUMMARY {'PASS': 1264}`,
no REJ or FAIL rows. The total checks against the parts: 1209 manifest
rows, 6 FILE positives, 4 DBF acceptance tests, 37 thread programs (three
runs each) and 8 EXTERNAL demos.
- FILE: compared with the committed Linux expectations, using
  `check.py`'s fixture tree.
- DBF: compared with the committed Linux expectations. The resulting

- Threads and EXTERNAL: compared with Linux runs of the same programs,

  that Linux output is also equal, CR removed, to native Windows runs.
- x86 Linux and Windows assembly is still byte-identical to `a21bc01c`:
  3644 compilations, 0 diff.

## EXTERNAL with threads, and Mach-O Intel (17 November 2026)

- EXTERNAL with threads, every target: the bridge channel
  (`hbc_ext_argc/argv/ret_tag/ret_pay`) is process global, so a threaded
  program serializes EXTERNAL calls with a recursive lock owned by the
  thread block (`%fs:120`). A C function that evaluates an hbc codeblock
  may call EXTERNAL again on the same thread. The lock is held while C
  evaluates a codeblock: a codeblock that waits for another thread which
  needs EXTERNAL deadlocks.
- Mach-O ARM64: the C ABI thunks keep the emulated stack and `%fs` record
  per thread in a pthread TSD key (`__a64_tkey`, created at entry).
- Thread stack alignment: `hbc_thread_boot` now aligns the stack before
  the thread function. Workers used to run 8 bytes off the SysV
  alignment; C reached from a worker could fault on aligned SSE stores
  (seen on Linux with gcc's `hb_retnd`).
- Mach-O Intel: see [MACHO-INTEL.md](MACHO-INTEL.md). DBF, FILE, threads,
  EXTERNAL and the macro operator now work there too.

Evidence (GitHub Actions run 44032525274, branch `macho-intel-dyld`):
`tests/run_macho_arm64.py` reports `SUMMARY {'PASS': 1274} (FULL battery)`
on both `native-arm64` (macos-15, Apple Silicon) and `native-intel`
(macos-15-intel, `--target macho`). The runner enforces the total:
1218 manifest rows + 6 FILE + 4 DBF + 37 thread programs + 9 EXTERNAL
demos. The `m_clie.dbf` SHA-256 of DBF tests 4-7 is the same on both
Macs. x86 Linux and Windows assembly of the manifest is byte-identical
to main `ffda998d` (3656 compilations, 0 diff).

## ARM64 named limit retired: hb_idleSleep (17 November 2026)

`hb_idleSleep` lowers to Linux syscall 35 in the shared x86 runtime.
Darwin has no equivalent BSD timespec-pointer syscall: 334 is
`__semwait_signal`, with different arguments and a semaphore requirement.
The ARM64 translator instead calls the stable `_nanosleep` ABI from
libSystem, already linked by the backend, through a new MIT-owned wrapper.
The wrapper passes rqtp/rmtp in x0/x1, preserves mapped caller-saved GPRs,
TLS/atomic scratch, NZCV and full XMM0-15, and converts libc's 0/-1+errno
return into 0/negative errno. Only the documented nanosleep errors
EINTR/EFAULT/EINVAL (4/14/22 on both systems) have Linux-compatible
numbers. Other Darwin errno values pass through numerically, without a
universal errno mapping: for example Darwin ENOSYS=78 differs from Linux
ENOSYS=38. The hb_idleSleep caller ignores the return value. This is not
a general Linux syscall-errno compatibility layer.
Static syscall 35 and the dynamic dispatch route share this wrapper.
No Apple implementation code is copied.

The five former named-rejection rows now execute on ARM64. Intel
followed the same day: `darwin_dyld_asm` lowers a constant Linux 35 to
`hbc_dw_nanosleep`, which calls libSystem `nanosleep` (and `__error`)
through dyld GOT slots, preserving rdi/rsi/rdx/r8-r10 and xmm0-15 like
the syscall instruction, with the same 0/negative-errno result. The
two imports are bound only when the program sleeps. Neither target has
named EXPECTED_REJ entries now; full total is 1279 PASS on both,
including the new apithreads EXTERNAL demo.
 Native timing uses the
same monotonic windows as the Linux suite, including upper bounds and
no-op forms, and prints the measured durations. Native PASS remains
unclaimed until macOS CI witnesses it. Linux/Windows runtime is unchanged.

(History: the limit was introduced with five `EXPECTED_REJ` rows in the
same commit that reworded five runtime-assembly comments whose first
word was a C-preprocessor directive (`# error`, `# line`): clang

preprocesses `.s` files, so those comments aborted the macOS
feasibility job's assemble step (run 44035714366). A unit test scans
the emitted runtime for directive-word comments on both native
targets.)
