# Integer overflow stops instead of wrapping (21 November 2026)

## Behaviour

Until now hbc checked fixed-i64 `+`, `-` and `*` for overflow only in
functions with a STATIC or a by-reference parameter. Everywhere else the
result wrapped silently: `9223372036854775807 + 1` printed
`-9223372036854775808`. Harbour 3.2 promotes the value to a double instead
(oracle, native Windows hbmk2 -gtstd: `9223372036854776000`, and
`9223372036854776000.00` for `*`).

The check is now on in every function. An overflowing `+`, `-`, `*`, unary
minus, `x op= e` or fixed-array `a[i] op= e` stops the program with

    Limit: integer overflow needs numeric promotion
    Callstack:
      at main (file.prg:line)

and exit status 1, before the result is stored. Full numeric promotion
stays a named boundary, as it already was for STATIC, by-reference and
increment operands. The message replaces the former
`Limit: static/byref integer arithmetic needs numeric promotion`, which
named only the old scope.

## Coverage

Probes (one per program, base compiler vs this change vs Harbour):
immediate, variable and call right operands for `+`, `-` and `*`; unary
minus of MIN; `x := x + 1`; `+=`, `-=`, `*=` on a local; `+=` and `*=` on a
fixed array cell; a read of an array cell in an expression; a PRIVATE with
`+=` and in an expression; `++`; Dyn locals (`local a, b` assigned later)
with `+`, `-`, `*` and unary minus. All of them wrapped before and stop now.
Controls that must not stop still print the same as Harbour: `MAX + 0`,
`MAX - 1 + 1`, `MIN + 1`.

Not covered: `h[k] op= e` and `a[i] op= e` on dynamic arrays are rejected
at compile time by hbc (unchanged). `3037000499 * 3037000499` fits in i64
and hbc prints the exact product, while Harbour prints
`9223372030926248960`: Harbour's multiplication overflow test is
conservative. That divergence is not changed or pinned here.

Rows: `tests/i64-overflow/*.prg` (7 `posx` rows), each with non-stopping
controls before the stopping expression.

## Verification (native Windows 11)

- Manifest differential, base vs this change, Windows, Linux and Windows
  `--instrument` assembly: 1901 programs, no compile result changes. The
  asm of 1277 changes, most of them only through the shorter message in
  the shared runtime data; with the check alone (old message) 201 change.
  The 1277 rows built and run on Windows, plain and `--instrument`: stdout,
  stderr and exit status identical except the 7 new rows, which wrap under
  the base compiler.
- `tests/dyn-dyn-plus/check.py`: same pass/fail set before and after (the
  `mem-*` rows need Linux in both).
- Loop register promotion still applies to the same 17 loops in 13 rows.

## Cost

Each checked operation adds one `jo` to a shared exit, and a statement
that contains one keeps its trace write. In call-free integer loops that
`src/loopreg.rs` keeps in registers this is visible.

On this CPU (Xeon W-2140B, Skylake, affected by the JCC erratum) the
figures depend on code layout: a jump that crosses or ends on a 32-byte
boundary runs slowly, and where the jumps land changes with every edit. So
each loop was measured in two layouts: the compiler's default output, and
the same assembly built with GNU as `-mbranches-within-32B-boundaries`,
which pads every jump and takes layout out of the comparison. Process
cycles, minimum of 7 runs, 500-800 million iterations; cycles and CPU time
agree on every binary.

| loop | default: before | after | change | padded: before | after | change |
|---|---|---|---|---|---|---|
| `s := s + i * k - 1` with a conditional subtract | 4.56 G | 5.85 G | +28 % | 3.74 G | 4.78 G | +28 % |
| `n := n + i` with a conditional subtract (`bench/b1_int.prg`) | 4.34 G | 7.34 G | +69 % | 4.31 G | 5.65 G | +31 % |
| same with a nested condition (`bench/b1b_int_bounded.prg`) | 5.52 G | 8.64 G | +56 % | 5.49 G | 6.78 G | +23 % |
| one call per iteration (`bench/b3_call.prg`) | 3.15 G | 3.18 G | +1 % | | | |

With layout taken out, the check costs 23-31 % on these promoted loops,
and nothing measurable when the loop body makes a call. In the default
layout the cost ranges from 28 % to 69 %, depending on where the jumps land.

Possible follow-ups:

- **Jump padding in the internal assembler.** This is the layout fix
  itself: aligning only the loop head is not enough. Done: see
  `docs/HASM-BRANCH-ALIGN-2026-11-21.md`.

## Per-statement overflow stubs

A statement whose only way to stop is the overflow check no longer writes
its trace location. Each such statement that contains a checked operation
gets one stub, emitted after its function:

    .Lovs0:
        lea .LstrN(%rip), %r11      # the statement's location, as the
        mov %r11, -80(%rbp)         # trace write would have stored it
        movq $len, -72(%rbp)
        jmp hbc_static_overflow

Its `jo` instructions jump there instead of to the handler. A statement
that still writes its trace (it calls, indexes, or has a Dyn operand) jumps
straight to the handler, as before. Callstacks are unchanged:
`tests/i64-overflow/loop.prg` stops inside a promoted loop (the loop's exit
stub stores the registers back, then reaches the overflow stub) and
`tests/i64-overflow/callee.prg` stops in a callee with a two-frame
callstack.

Cost, same benchmarks and method as above. Padded is GNU as
`-mbranches-within-32B-boundaries`; cycles and CPU time agree.

| loop | padded: base | check | check + stubs | default: check + stubs |
|---|---|---|---|---|
| `s := s + i * k - 1` | 3.74 G | 4.78 G (+28 %) | 4.16 G (+11 %) | 5.86 G |
| `bench/b1_int.prg` | 4.31 G | 5.65 G (+31 %) | 4.65 G (+8 %) | 6.65 G |
| `bench/b1b_int_bounded.prg` | 5.49 G | 6.78 G (+23 %) | 5.81 G (+6 %) | 5.83 G |

The default-layout column again moves with jump placement.

Verification (native Windows 11): manifest differential against the check
alone, covering 1903 programs and Windows, Linux and Windows
`--instrument` assembly. Compile results are unchanged. The assembly of 93
rows changes, and those rows built and run plain and `--instrument` give
identical stdout, stderr and exit status. Loop register promotion still
covers the same loops (18 in 14 rows, counting the new `loop.prg`).
